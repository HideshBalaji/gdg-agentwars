Hi, we’re the Ghost Dispatcher team. Our problem statement is Logistics Handler. In one line: when a refrigerated truck carrying vaccines breaks down in the middle of the night, our agents find a replacement truck, book it, re-route the cargo and notify everyone — and keep going when their own tools fail. Everything you’ll see is built on Google ADK and Gemini, with an MCP server for logistics data.

These are real incidents. In Mendocino County a hospital freezer failed around 2 a.m. and 830 doses had roughly two hours. In Maine, 4,400 Moderna doses went out of range in transit; sensors caught it, but the response — re-planning, reshipping — was manual. Industry-wide, IQVIA estimates about 35 billion dollars a year lost to temperature-controlled logistics failures, and the WHO estimates up to half of vaccines are wasted, with the cold chain a main cause. Be honest: the Mendocino case was a storage freezer, not a truck.

Today: one dispatcher, 30–50 drivers, a phone, and the middle of the night.

Ghost Dispatcher rescues the load before anyone wakes up.

Today this is a human job: a dispatcher at a large carrier can be looking after 30 to 50 drivers, and the response happens by phone, at night, under a hard spoilage deadline. Ghost Dispatcher turns that into an automated loop — and the important word is “self-healing”: it keeps going even when the systems it depends on fail.

Left to right: the React control room talks to a FastAPI backend over REST and a server-sent event stream. The backend runs an ADK team — a Dispatcher plus seven specialists. Agents never touch the world directly: they call deterministic services that plan, validate and execute, with retry, circuit-breaker and fallback logic, and persist to SQLite. 07

This is real ADK orchestration, not one prompt pretending to be eight agents. The Dispatcher runs on Gemini Pro and hands the conversation to specialists on Flash using ADK’s agent transfer. Whoever owns the conversation answers the user directly — ask “why this vehicle?” and Route & Risk answers. Handovers are capped at four per message, planning and validation run in a bounded LoopAgent of at most three tries, and ownership is stored in the ADK session so it survives restarts. Validator and Watchdog lean on deterministic code, not the model.

This is the most important design decision. The model suggests plans; deterministic Python decides whether they are allowed. Of six candidates, the cheapest is a dry van, one doesn’t have the capacity, one driver is out of hours — all rejected with a reason the UI shows. Learned preferences can only re-rank plans that already pass. Nothing an agent says, and nothing in a driver’s message, can turn off a hard check.

Self-healing

We kill the carrier mid-booking. It finishes anyway.

Retry ×3 fails

Circuit opens

Re-plan without it

Booked via backup

Never double-booked

Idempotency keys. Uncertain timeouts are reconciled, not resent.

Tool-call repair

One corrected retry after a schema error, never invented IDs.

Learned workaround

An unhealthy carrier is skipped until it is probed again.

Every step appears live in the Healing Log

10

You saw this in the demo. When the carrier API dies mid-booking, the Watchdog retries with backoff, opens a circuit on that carrier for 60 seconds, re-plans without it, and books the next feasible truck through a backup carrier. The subtle part is safety: bookings carry idempotency keys, and if a timeout leaves the outcome unknown we reconcile by booking ID rather than resending, so we never book two trucks. Tool-call errors get exactly one corrected retry, and the system remembers which carriers are unhealthy.

11

The Critic turns a human rating into a typed preference: if we can save at least five thousand rupees by arriving at most ninety minutes later, still inside both deadlines, prefer the cheaper carrier. It’s scoped to the customer and cargo profile, it expires, and it only re-ranks plans that already passed every hard check. Free-text feedback is stored as data, never executed. The cost drop from 18,500 to 12,000 rupees on a comparable incident is reproduced by make demo on every CI run.

Deterministic redaction, tested against both SQLite stores and the event stream

13

Drivers and customers type real things into chat — phone numbers, ID numbers. A deterministic redaction layer runs at the API boundary before anything is stored, and again in an ADK callback before any text reaches Gemini, so the model never sees raw personal data. Agent replies are filtered on the way out too. We redact Indian and international phone numbers, Aadhaar, PAN, Luhn-checked card numbers and emails, and log only the type that was redacted. Tests assert the raw values never appear in either database or the event stream — and that logistics IDs like TN-07 aren’t falsely redacted.

14

We don’t just ask the model not to hallucinate; we measure it. Groundedness: we extract every truck ID, rupee amount and time from an agent’s reply and check each one appears in the tool results from that same turn. Truthfulness: an agent may never say “booked” unless the execute tool returned a receipt, and offline output must be labelled simulated. Trajectory: for each scenario — breakdown, carrier outage, the rejection cases — we assert the expected handovers and tool calls. The offline suite runs in CI on every push; in live mode the same scenarios run as ADK eval sets with an LLM-judge rubric.
